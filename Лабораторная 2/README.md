## Как модель выводится из требований

На защите нужно уметь объяснить, почему модель устроена именно так. Каждое отношение и каждый атрибут
должны обосновываться требованием заказчика, а не появляться «потому что так принято».

1. **Описание бизнес-процесса.** Клиент приносит устройство → приёмщик оформляет заказ и выдаёт квитанцию →
   инженер делает диагностику → стоимость согласуется с клиентом → выполняются работы, ставятся запчасти →
   клиент платит и забирает устройство → при поломке в гарантийный срок оформляется гарантийный заказ.
2. **Требования заказчика.** Из процесса выписываются функции, которые нужны фирме (15 пунктов в отчёте),
   и ограничения на данные (7 пунктов).
3. **Выделение сущностей.** Существительные из требований: клиент, устройство, заказ, сотрудник, услуга,
   запчасть, поставщик, поставка, оплата, статус. Если у понятия есть собственные атрибуты или
   на него ссылаются несколько других понятий, оно становится отдельным отношением.
4. **Справочники.** Значения, которые повторяются у многих записей (должность, тип устройства,
   производитель, статус), вынесены в отдельные отношения. Так нет дублирования текста и опечаток.
5. **Связи M:N.** «Заказ — услуга», «заказ — запчасть», «поставка — запчасть» разрешены
   через отношения-связи, потому что у связи есть свои атрибуты: количество и цена.
6. **Ключи.** Во всех отношениях суррогатный PK `id`. Естественные ключи (номер квитанции, артикул, УНП,
   пара «производитель + серийный номер», пара «поставщик + номер накладной») объявлены уникальными.
7. **Проверка избыточности.** Всё, что можно вычислить, удалено из модели: итоговая сумма, текущий статус,
   дата выдачи, остаток на складе.

## Ключевые решения и их обоснование

| Решение | Почему |
|---|---|
| Физлица, ИП и организации в одной таблице `clients` | Отличаются только двумя необязательными атрибутами: `unp`, `contact_person`. Отдельные таблицы дали бы дублирование связей с устройствами |
| Устройство — отдельное отношение, а не атрибуты заказа | Одно устройство ремонтируется многократно, нужна история ремонтов (требование 2) |
| В заказе нет `client_id` | Клиент определяется через устройство (`devices.client_id`). Хранить его в заказе — избыточность и риск противоречия |
| Две связи заказа с сотрудниками: `receiver_id`, `engineer_id` | У сотрудников разные роли. `engineer_id` необязательный, пока инженер не назначен |
| Рекурсивная связь `warranty_order_id` | Гарантийный заказ ссылается на исходный, по нему проверяется гарантийный срок (требование 13) |
| Отдельная `order_status_history` вместо одного поля статуса | Нужны дата, время, сотрудник и комментарий каждой смены (требование 6). Текущий статус — последняя запись |
| `price` в `order_services` и `order_parts` | Цена фиксируется на момент операции. Изменение прайса не меняет старые заказы (требование 8) |
| `engineer_id` в `order_services` | Отдельную работу может выполнить не ответственный инженер заказа (выработка инженеров — требование 15) |
| Нет `stock_quantity` у запчастей | Остаток = Σ `supply_items.quantity` − Σ `order_parts.quantity` |
| `payments` — 1:M к заказу | Предоплата за запчасти и оплата частями (требование 12) |
| Поставка разделена на `supplies` и `supply_items` | В одной накладной много позиций. Иначе номер накладной, дата и поставщик повторялись бы в каждой строке |

## Вероятные вопросы

**Чем инфологическая модель отличается от даталогической?**
Инфологическая (концептуальная) описывает предметную область без привязки к СУБД: сущности, атрибуты, связи.
Даталогическая — та же модель, переведённая в конкретную модель данных и СУБД (таблицы, типы данных, индексы,
ограничения).

**Что такое первичный, потенциальный, альтернативный, внешний, суррогатный ключ?**
- Потенциальный ключ — минимальный набор атрибутов, однозначно определяющий кортеж.
- Первичный ключ — потенциальный ключ, выбранный основным.
- Альтернативный ключ — остальные потенциальные ключи. Здесь это `order_no`, `article`, `unp`.
- Внешний ключ — атрибут, ссылающийся на первичный ключ другого (или того же) отношения.
- Суррогатный ключ — искусственный, без смысла в предметной области (`id`).

**Почему суррогатные ключи, а не естественные?**
Естественные значения могут меняться (номер телефона, серийный номер введён с ошибкой) или отсутствовать (УНП у
физлица). Суррогатный ключ неизменен и компактен. Естественные ключи всё равно защищены ограничением UNIQUE.

**Какие типы связей есть в модели?**
- 1:M — большинство связей (клиент → устройства).
- M:N — через отношения-связи (`order_services`, `order_parts`, `supply_items`).
- Рекурсивная — `repair_orders.warranty_order_id`.
- Связь 1:1 в модели не понадобилась.

**Что такое ссылочная целостность и как она обеспечивается?**
Внешний ключ не может ссылаться на несуществующую запись. Действия при удалении в модели:
- клиента, устройство, сотрудника, услугу, запчасть, на которые есть ссылки, удалять запрещено (RESTRICT);
- строки заказа (история статусов, работы, запчасти, оплаты) и позиции поставки удаляются вместе с родителем
  (CASCADE). На UML это показано композицией.

**Почему композиция на диаграмме только у некоторых связей?**
Композиция означает, что часть не существует без целого: работа по заказу без заказа не имеет смысла. Устройство
без клиента теоретически имеет смысл, поэтому там обычная ассоциация.

**Где хранится итоговая стоимость заказа?**
Нигде, она вычисляется: Σ(`order_services.quantity × price`) + Σ(`order_parts.quantity × price`).
Задолженность = стоимость − Σ `payments.amount`.

**Как узнать, что заказ просрочен?**
`due_date` меньше текущей даты, а последний статус заказа не является завершающим (`order_statuses.is_final = false`).

**Почему 17 отношений?**
Каждое отношение закрывает конкретное требование заказчика (см. таблицу выше). Объединить нельзя, не нарушив
нормализацию или не потеряв данные требования.
